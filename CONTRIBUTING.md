# Contributing

Thank you for helping. A few rules keep honestcv predictable.

## How to propose a change

1. Fork the repository on GitHub, using the Fork button.
2. Make your change on a branch of your fork.
3. Run the tests: `uv run pytest -q -rs`. They run offline; a test that opens a network connection fails.
4. Open a pull request against `main` and describe what changes for a user.

## What needs maintainer review

- `tests/golden/` holds the acceptance fixtures: the worked scoring example, the expected checker flags, the sample run. They change only with maintainer review, in a pull request that says why.
- `src/honestcv/samples/` is the fictional demo workspace. It changes only with maintainer review, because the demo output and the golden fixtures depend on it.
- `src/honestcv/sources/registry.yml`: a new source needs a reading of its terms and robots.txt, recorded with the date. honestcv reads only documented public APIs whose terms allow automated access. Every other site stays an import path (file or paste).

## Ground rules

- No model calls, no new runtime dependency, no telemetry.
- Scoring rules live in configuration and data files, not in code. `docs/scoring.md` is generated by `render_rubric`; regenerate it when the rules change.
- Test data is fictional: invented people and companies, domains ending in `.invalid`, no phone numbers, and e-mail addresses only at `example.invalid`.
- User-facing text is plain English with short sentences.
- Every list built from a set is sorted before it is stored or printed, so output never depends on input order.
